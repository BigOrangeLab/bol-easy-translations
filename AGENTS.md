# AI Agent Instructions — BOL Easy Translations

This is a WordPress block plugin developed by George Stephanis / Big Orange Lab.
It provides two Gutenberg blocks: **Localized Content** (parent) and **Translation** (inner).

---

## Key facts

- **Plugin slug:** `bol-easy-translations`
- **Block namespace:** `bol`
- **Block names:** `bol/localized-content`, `bol/translation`
- **Registration:** uses `wp_register_block_types_from_metadata_collection` (WP 6.7+ manifest API)
- **Build tool:** `@wordpress/scripts` (webpack) — source in `src/`, output in `build/`
- **No PHP render callbacks** — both blocks use static `save()` functions; all front-end interactivity is in `src/localized-content/view.js`

## File map

| Path | Purpose |
|---|---|
| `bol-easy-translations.php` | Plugin header + single `init` hook that registers both blocks |
| `src/localized-content/` | Parent block source |
| `src/localized-content/view.js` | Front-end language switcher (vanilla JS, no dependencies) |
| `src/translation/` | Inner block source |
| `build/blocks-manifest.php` | Auto-generated by `npm run build` — do not edit by hand |
| `package.json` | npm scripts; `npm run build` compiles everything |

## Development workflow

Always run a production build after editing source files:

```bash
cd wp-content/plugins/bol-easy-translations
npm run build
```

If working inside a WordPress Studio site, the site does not need to be restarted after a build — file changes are picked up immediately.

## Block relationship rules

- `bol/translation` declares `"parent": ["bol/localized-content"]` and `"inserter": false` in `block.json`, so it can only exist inside a Localized Content block and cannot be inserted standalone.
- The Localized Content edit component passes `allowedBlocks={['bol/translation']}` to `InnerBlocks`, enforcing this on the editor side as well.
- A default `template` of two Translation blocks (en / es) is applied when the parent block is first inserted.

## Front-end switcher contract

The view script (`src/localized-content/view.js`) relies on this DOM structure being present:

```html
<div class="wp-block-bol-localized-content">
  <div class="wp-block-bol-translation" data-locale="en" data-label="English" lang="en">…</div>
  <div class="wp-block-bol-translation" data-locale="es" data-label="Español" lang="es">…</div>
</div>
```

- `data-locale` is the locale code written from the `locale` block attribute.
- `data-label` is the display name written from the `label` block attribute.
- The script inserts a `<nav class="bol-language-switcher">` as the first child of the container.
- Active translation is shown; others receive `hidden="true"` and `aria-hidden="true"`.
- Preferred locale is persisted in `localStorage` under `bol-preferred-locale`.

**Do not change the CSS class names or data attributes** in `save.js` without also updating `view.js` and the frontend stylesheet.

## Styling conventions

- Front-end + editor shared styles: `src/*/style.scss` → compiled to `build/*/style-index.css`
- Editor-only styles: `src/*/editor.scss` → compiled into `build/*/index.css` (loaded only in the block editor)
- BEM-style class names are used: block is `bol-language-switcher`, elements are `bol-language-switcher__tab`

## What to avoid

- Do not edit files inside `build/` directly — they are overwritten on every build.
- Do not add PHP render callbacks unless you have a specific reason; the static save approach is intentional and simpler.
- Do not change the `parent` constraint on `bol/translation` without also updating the `allowedBlocks` prop in the Localized Content edit component.
